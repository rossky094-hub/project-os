# Project OS Alpha 产品目标

## 面向谁、解决什么

目标读者是刚接手代码库、尚不能从目录和提交数判断项目进展的人。工作台应让他先说明想完成的用户结果，再看到已登记来源支持的现状、目标差距、下一步开发的预期作用和实际验证状态。初次选择来源、解释业务目标、确认条件和配置独立检查，目前仍需要熟悉项目的人参与。

一次有用的判断至少回答：

1. 人的原始目标及可核对条款是什么，哪些条款尚未被准确理解？
2. 已登记代码支持哪些用户旅程和实现关系，读取缺口在哪里？
3. 哪些差距有来源支持，哪些只是尚待排查的假设？
4. 这一轮开发要改变哪一步，预期改善什么，实际观察到什么来源变化？
5. 哪些确认条件有同目标、同来源、同轮次的独立回执；哪些仍失败或未知？

产品主线是目标 → 已观察现状 → 差距 → 下一步开发 → 预期作用 → 验证 → 进展判断。下一轮从仍未满足的目标继续，而非把轮次终结、代码增长或模型总结当作交付完成。

## 用户路径

用户显式登记一个项目的来源范围与可选证据根，检查清单后填写或修订目标。模型只读分析已提供的源码片段，形成实际与期望的用户旅程、模块及关系、来源引用、差距、竞争解释和建议。用户逐条核对模型提出的场景及可观察条件，必要时修改并确认。开发活动通过登记的轮次或选定的 Codex 事件流进入；用户把轮次与当前目标和产品主线人工关联。之后观察前后来源，并运行事先登记的本地检查，核对其与已确认条件的对应关系。工作台保留旧版本与失败证据，显示当前仍能成立的有限结论。

界面必须把三层关系分开：

| 层 | 回答的问题 | 不可推断 |
| --- | --- | --- |
| 产品主线 | 用户从入口到结果经过哪些实际或期望步骤，何时分支、反馈？ | 步骤相邻或模块 import 不证明业务顺序 |
| 实现关系 | 哪些模块以调用、数据、依赖等方式相连？ | 静态引用不证明已运行或目标达成 |
| 开发轮次及证据 | 开发意图、源变化、人工关联和条件回执怎样改变判断？ | Agent 报告或命令退出码不证明条件通过 |

## 状态与证据

来源引用只支持其实际提供的行和登记范围。读取上限、跳过文件、缺行、未映射旅程、条件与证据冲突都应显示为有限覆盖或未知。模型可提出修复建议，但不替人修改目标、确认条件或给出运行已验证状态。

每个进展判断需要保留目标版本、来源 hash、分析视图、确认场景、轮次及检查断言到条件的映射。只有当前绑定有效、检查原文可重算且结果与条件相符，才显示限定的条件进展。来源或目标变化后，旧关联作为历史继续可查，当前判断重新核对。

## Alpha 边界

本版是本机受信环境下运行的源码预览。只扫描用户登记的范围；分析会把选定源文本发送给配置的 Codex CLI。服务只监听本机 127.0.0.1，验证命令仅从本地配置读取，HTTP 不能提交任意 shell 命令。没有生产托管、自动开发批准或通用项目理解保证。

Alpha 的技术检查包括可安装的锁文件、类型检查、导出测试、本机启动和页面资源，以及来源 manifest 的字节比对。产品结论仍须另看真实同案例的分析、人工关联、前后观察、条件回执、重启连续性和桌面阅读证据。独立新手能否无需专家看懂、陌生项目是否可靠，均未验收。
